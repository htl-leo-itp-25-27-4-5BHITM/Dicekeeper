# Design

## Context

See `proposal.md` for motivation and `specs/account-deletion/spec.md` for the behavior contract.

The current endpoint calls Keycloak before starting local cleanup. `KeycloakAdminService` uses a client whose service account is not enabled, makes unbounded synchronous HTTP calls, and reduces provider failures to exception strings. LeoCloud supplies the confidential client through `KEYCLOAK_CLIENT_ID` and `KEYCLOAK_CLIENT_SECRET`; Keycloak rejects `client_credentials` until that client's service account is explicitly enabled.

Local cleanup is one database transaction, but filesystem deletion and Keycloak are not part of that transaction. It also deletes owned-campaign memberships before collecting every affected character identifier, so some now-unreferenced characters can escape cleanup. Separately, `SecurityIdentityService` automatically creates a missing player for any authenticated subject; that behavior can resurrect an account after a partial deletion or from another still-valid browser session.

The application has no database migration framework and currently relies on Hibernate `update`. The public request path includes Cloudflare and two Nginx hops, so the client cannot assume an error body was generated by Dicekeeper even when the request reached the account endpoint.

## Goals / Non-Goals

**Goals:**

- Coordinate database, filesystem, and Keycloak deletion so every intermediate state is explicit and safely retryable.
- Prevent a deleted or pending-deletion identity from recreating a player through an existing OIDC session.
- Use the configured Keycloak client's least-privilege service account with explicit deployment configuration.
- Keep provider waits bounded and make failures diagnosable without leaking secrets or personal data.
- Preserve the current authenticated self-delete entry point while giving the frontend a stable, safe error contract.
- Make local cleanup deterministic for empty and populated accounts.

**Non-Goals:**

- Replacing Keycloak, Quarkus OIDC, Cloudflare, or the public edge design.
- Building a general-purpose distributed job framework.
- Allowing administrators to delete arbitrary users through the Dicekeeper API.
- Changing campaign ownership semantics or retaining a deleted owner's campaigns.
- Making the development deployment capable of deleting shared-realm identities unless its service account is deliberately enabled and reviewed.

## Decisions

### 1. Use the configured confidential client's service account

Use the environment's configured confidential client, enable its service account, and grant that service account only the realm-management permission required to delete users. Production supplies `KEYCLOAK_CLIENT_ID` and `KEYCLOAK_CLIENT_SECRET`; development uses its own environment-specific values under the same deployed names.

When deletion is enabled, missing or placeholder client configuration will fail a dedicated readiness check and make the deletion capability unavailable. Development remains disabled by default and can opt in only after its client service account is reviewed. Deployment automation will require the existing client secrets and will never print their values.

Trade-off: enabling `manage-users` on `dicekeeper-web` couples browser login and service-account administration in one client. This follows the deployed credential contract supplied for this environment, while still isolating privilege to the non-human service-account principal and limiting it to `manage-users`. Alternative: let users delete themselves through the Keycloak account console. Rejected because Dicekeeper still has to coordinate application data cleanup and prevent partial results.

### 2. Persist a small deletion state machine around irreversible work

Add an account-deletion marker keyed by a SHA-256 digest of the high-entropy Keycloak subject. It stores the original player identifier, state, timestamps, a bounded failure category, and a cleanup manifest containing only internal relative file paths. It does not store email, display name, credentials, access tokens, provider response bodies, or raw exception text.

The synchronous flow is:

```text
ACTIVE
  |
  | validate owner + obtain admin token
  v
PREPARED
  |
  | one DB transaction: create marker, collect cleanup manifest,
  | delete related rows and player
  v
LOCAL_DELETED
  |
  | delete recorded files; retry without hiding failures
  v
FILES_DELETED
  |
  | Keycloak DELETE (204 and 404 are both complete)
  v
COMPLETED
```

If administrative authentication or provider reachability fails before `PREPARED`, no local mutation occurs. Failures after the local transaction leave the marker at the last completed state; the same authenticated subject can repeat the endpoint and resume from that state. A retry does not require the `Player` row to still exist: ownership is validated against the marker's subject digest and original player identifier.

Files are removed before the Keycloak identity because file deletion is not transactional and can fail. This preserves an authenticated retry path until all Dicekeeper-owned data is gone. Once Keycloak returns 204 or 404, all required local and file cleanup has already completed.

Alternative: keep the existing Keycloak-first sequence. Rejected because a later database failure removes the user's ability to retry while leaving their application data behind. Alternative: delete local data first with no marker. Rejected because automatic player creation can recreate the account and there is no durable record of unfinished work. Alternative: add an asynchronous queue. Rejected as unnecessary operational infrastructure for a user-driven flow that can resume synchronously.

### 3. Block account recreation while a marker is active

Before creating a player, identity resolution will compute the subject digest and check account-deletion state. A pending marker produces a stable `ACCOUNT_DELETION_PENDING` response and permits only the deletion-resume path; a completed marker produces an account-gone response. It never creates a replacement player.

Completed markers will be retained for a configured period no shorter than the maximum accepted OIDC token/session lifetime, preventing another device with stale session state from recreating the account. The marker contains no direct profile fields. The operational guide will keep the retention setting aligned with Keycloak and Quarkus session policy.

Alternative: remove the marker immediately after Keycloak deletion. Rejected because deleting a Keycloak user does not retroactively erase every already-issued browser token or application session cookie. Alternative: permanently retain the raw Keycloak subject. Rejected because a digest is sufficient for matching a presented identity and minimizes retained identity data.

### 4. Make local cleanup set-based and order-safe

The local transaction will first collect the complete affected set: owned campaigns, all their memberships, the deleting player's remaining memberships, notifications, file paths, and every referenced character candidate. It will then delete campaign-dependent records, memberships, user notifications, and the player. Only after all affected memberships are gone will it delete candidate characters whose reference count is zero, including their ability and skill rows.

The same transaction can be repeated safely when some rows are already absent. Missing records are completion conditions, while authorization is anchored to the current identity or its existing marker rather than the continued presence of the player row.

Alternative: rely on entity cascades. Rejected because the current model mostly stores scalar identifiers rather than mapped foreign-key relationships and has no ownership link on `Character`; introducing broad cascades would be a larger data-model redesign.

### 5. Use typed provider outcomes, deadlines, and structured logging

Keycloak token and delete requests will have configurable connection and per-request deadlines. The admin service will translate failures into bounded categories such as `CONFIGURATION`, `AUTHENTICATION`, `AUTHORIZATION`, `TIMEOUT`, `TRANSPORT`, and `UPSTREAM_STATUS`. It will not propagate provider bodies or raw exception messages to the resource response.

Server logs will include the deletion stage, failure category, safe HTTP status when present, and an internal correlation identifier. They will exclude client secrets, bearer tokens, raw subject identifiers, email addresses, profile fields, and full upstream bodies.

Alternative: keep returning exception messages. Rejected because it exposes implementation details to users, provides an unstable API, and currently leaves no application log for a caught failure.

### 6. Return a bounded API contract and distrust intermediary bodies in the UI

Introduce `DELETE /api/account` as the subject-scoped coordinator endpoint so a pending deletion can resume even after its `Player` row is gone. The existing `DELETE /api/player/{id}` route remains as a compatibility wrapper: it verifies that the requested player belongs to the current subject and delegates to the same coordinator. The profile view will use the subject-scoped endpoint for new requests.

Completion remains `204 No Content` with `Clear-Site-Data: "cookies", "storage"`. Application-generated failures use JSON with bounded fields:

```json
{
  "code": "ACCOUNT_DELETION_RETRYABLE",
  "message": "Der Account konnte noch nicht vollständig gelöscht werden. Bitte erneut versuchen.",
  "retryable": true
}
```

Authorization remains 403. Preflight/provider unavailability returns 503 with a retryable code while the account is unchanged. A persisted partial state returns 409 with `ACCOUNT_DELETION_PENDING`; invoking the same deletion request resumes it. An unexpected local transaction failure returns 500 after rollback. The endpoint will not use 502 for its own failures because Cloudflare treats that status as an origin-gateway failure and may replace the body.

The profile view will parse JSON only when the response content type is JSON, validate the bounded fields, and otherwise show a fixed generic German message. It will never render or concatenate HTML, plain upstream bodies, or exception details. Retryable states re-enable the button; completion clears cached player state and navigates to the public page. If `/api/auth/me` finds a pending marker after a reload or login from another device, it returns the same bounded `ACCOUNT_DELETION_PENDING` code and the login view offers a "Löschung fortsetzen" action that invokes the subject-scoped endpoint instead of attempting to recreate a player.

Alternative: depend on Cloudflare preserving the application body. Rejected because the reproduced 502 changed a 90-byte application response into a 6,405-byte Cloudflare page. Alternative: display all bodies through `textContent`. Rejected because it still leaks infrastructure details and creates an unusable page even without script execution.

### 7. Verify each boundary independently and then through the public route

Backend tests will cover token acquisition, user deletion, 404 idempotence, failure classification, deadlines, state transitions, authorization, complete local cleanup, rollback, and prevention of player recreation. Frontend tests will cover valid JSON, malformed JSON, text, and HTML responses. Browser coverage will exercise confirmation, retry UI, success navigation, and a routed HTML error without relying on live provider failure.

Deployment verification will confirm the configured client has service accounts enabled and only the required service-account role, the standard secret keys exist without exposing values, the application is ready, and a disposable account can be created and deleted through `https://dicekeeper.net`. Verification will also remove the exploratory test identity/player left by this investigation after the corrected flow is deployed.

## Risks / Trade-offs

- [A deletion marker retains a pseudonymous digest after profile removal] -> Store no direct identifiers, retain it only for the configured stale-session window, and document the retention policy.
- [A process crash can occur between an external action and the next marker update] -> Treat missing files and Keycloak 404 as success so the next retry can converge safely.
- [Development and production currently share identity infrastructure] -> Keep development deletion disabled unless explicitly provisioned with reviewed credentials; do not reuse production administrative secrets casually.
- [Filesystem cleanup can fail after the database commits] -> Persist a minimal cleanup manifest before commit and make file absence idempotent so a retry completes before identity deletion.
- [Hibernate `update` creates the marker table implicitly] -> Verify schema creation in development and production rollout; do not enable deletion until the table and readiness checks pass.
- [The `manage-users` realm role is powerful] -> Assign it only to the configured client's service-account principal, store the secret only in deployment secret stores, rotate it after suspected exposure, and test that the principal has no broader realm-management roles.
- [A user may close the browser while deletion is pending] -> On the next authenticated request, route the matching subject back to the resumable deletion state instead of recreating a player.

## Migration Plan

1. Add the deletion marker/state machine, order-safe local cleanup, typed Keycloak client, structured API responses, recreation guard, and automated tests while account deletion remains operationally disabled.
2. Add production deployment variables, GitHub secret validation, readiness checks, and an operations guide. Keep development disabled unless its own credentials are provided.
3. Enable the configured Keycloak client's service account, assign only the required user-management role, keep its identifier and secret outside the repository, and validate token and delete permissions with a disposable identity.
4. Deploy the application so the marker table is created, verify readiness and non-deletion account flows, then enable deletion in production.
5. Create a disposable account through the public route, exercise both a controlled failure and successful retry, and verify removal from Keycloak, application tables, and uploads without raw error content in the browser.
6. Use the corrected flow or an operator-documented equivalent to remove the exploratory account `codex-delete-empty-20261005-1309` / player `751`, then inspect logs for secret or personal-data leakage.

Rollback disables new deletion attempts and hides or disables the UI action while leaving the coordinator and recreation guard available for any marker that is already pending. Disable the configured client's service account or rotate its secret if the administrative configuration is suspect. Do not roll back to code that ignores pending markers until every pending deletion has been completed or explicitly repaired.
